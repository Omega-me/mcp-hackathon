# Data Model: People CRUD Operations

**Feature**: 005-peoples-crud
**Date**: November 20, 2025
**Purpose**: Define data structures, entities, and relationships for People CRUD feature

## Core Entities

### Person

Represents an individual in the system with contact information and team affiliation.

**Attributes**:

| Field     | Type   | Required        | Constraints                         | Description                                |
| --------- | ------ | --------------- | ----------------------------------- | ------------------------------------------ |
| id        | string | Yes (generated) | Non-empty, unique                   | Server-generated unique identifier         |
| firstName | string | Yes             | 1-255 chars, trimmed                | Person's first name                        |
| lastName  | string | Yes             | 1-255 chars, trimmed                | Person's last name                         |
| email     | string | Yes             | Valid email format, unique, trimmed | Person's email address (unique identifier) |
| teamId    | number | No              | Positive integer                    | Reference to team entity                   |
| createdAt | string | Yes (generated) | ISO 8601 timestamp                  | Record creation timestamp                  |
| updatedAt | string | Yes (generated) | ISO 8601 timestamp                  | Record last update timestamp               |

**Business Rules**:

- Email addresses must be unique across all people
- Email validation follows RFC 5322 standard
- First and last names cannot be empty after trimming
- teamId, when provided, must reference a valid team
- Timestamps are managed by the API server
- ID is generated by the API server on creation

**Relationships**:

- Person → Team (many-to-one, optional): A person may belong to one team
- Person ← Organization (assumed): People may be related to organizations through teams

### Create Person Schema

```typescript
/**
 * Schema for creating a person
 */
export const CreatePersonSchema = z.object({
  firstName: z
    .string()
    .min(MIN_NAME_LENGTH, ERROR_MESSAGES.FIRST_NAME_REQUIRED)
    .max(MAX_NAME_LENGTH, ERROR_MESSAGES.NAME_TOO_LONG)
    .trim(),
  lastName: z
    .string()
    .min(MIN_NAME_LENGTH, ERROR_MESSAGES.LAST_NAME_REQUIRED)
    .max(MAX_NAME_LENGTH, ERROR_MESSAGES.NAME_TOO_LONG)
    .trim(),
  email: z.string().email(ERROR_MESSAGES.INVALID_EMAIL).trim(),
  teamId: z.number().int().positive().optional(),
});

export type CreatePersonInput = z.infer<typeof CreatePersonSchema>;
```

**Validation Rules**:

- `firstName`: Required, 1-255 characters, trimmed
- `lastName`: Required, 1-255 characters, trimmed
- `email`: Required, valid email format (RFC 5322), trimmed
- `teamId`: Optional, positive integer

**Constants Used**:

- `MIN_NAME_LENGTH = 1`
- `MAX_NAME_LENGTH = 255`
- `ERROR_MESSAGES` from constants.ts

## Database Schema (API Side)

**Note**: This MCP server is stateless. The actual database schema is managed by the API server. Inferred schema:

```sql
CREATE TABLE people (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  first_name VARCHAR(255) NOT NULL,
  last_name VARCHAR(255) NOT NULL,
  email VARCHAR(255) NOT NULL UNIQUE,
  team_id INTEGER REFERENCES teams(id),
  created_at TIMESTAMP NOT NULL DEFAULT NOW(),
  updated_at TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_people_email ON people(email);
CREATE INDEX idx_people_team_id ON people(team_id);
```

**Assumptions**:

- PostgreSQL or similar relational database
- UUID for primary keys
- Unique constraint on email
- Foreign key to teams table
- Automatic timestamp management
